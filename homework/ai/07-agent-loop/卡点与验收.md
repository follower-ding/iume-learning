## 复述
- 第06课是一轮「提出调用 → 代码执行」；本课把「complete → 解析 → 执行或结束 → 写回消息」重复几次，并且规定一定会停。
- `run_agent` 默认 `max_steps=4`。每一轮只认三种走向：`final`（停，`stopped_reason=final`）；允许列表里的 `tool_call`（执行后写 `role="tool"` 再下一轮；参数非法写回「工具参数错误：…」，循环继续）；JSON 解析失败（消耗一步，把「只输出一个 JSON 对象」发回去，继续直到步数用尽）。
- 名字不在列表 → 不执行，`unknown_tool`。签名（工具名 + 排序后的参数 JSON）第二次出现 → 不执行第二次，`repeated_tool`。步数用尽 → `max_steps`，正式回答是「达到步数上限，已停止。」，即便工具已算出 30/60 元也不把最后一次价格升成答案。
- 相同 `hours=2` 算重复；每步换 1/2/3 小时不算重复，这时靠 `max_steps` 停。两个限制挡的不是同一种循环。
- Mock 直接读 `role="tool"`；真实 HTTP 客户端发送时把 tool 改写成 user 文本（部分兼容接口不接受 tool role）。启发式 Mock 见到工具结果就 `final`，正常计价两步；要观察「一直换参数」用 `script=`，脚本用完报错，不偷偷改回启发式。

## 原理（小白话）
- **为什么要两个刹车**：`max_steps` 挡「一直换参数」（签名每次不同）；`repeated_tool` 挡「同一调用死循环」（签名相同）。只留一个会漏掉另一种停不下来的情况。
- **为什么上限时不把工具价当答案**：工具结果在步骤记录里供排错；客人需要知道「这一轮不完整」。自动挑最后一次价格，等于悄悄补圆。
- **为什么解析失败也算一步**：不把异常冒出请求；消耗步数 + 写回「只输出 JSON」，既给模型改正机会，又保证步数上限仍有效。
- **为什么 tool 结果用 `role="tool"`，真客户端又改成 user**：循环内部语义清楚（哪条是工具返回）；对外兼容时部分接口不接受 tool role，所以改写成「工具 X 的结果：…」的 user 文本，内容仍是函数返回值。

## 口头自查（自己答）
1. `max_steps` 挡换参数的无限循环；`repeated_tool`（同名+同参签名）挡同一调用反复执行。
2. 上限时给客人「达到步数上限…」；正常计价给带「合计 N 元」的 final。工具价留在 steps 里，不自动升级成答案，避免把不完整轮次伪装成完整答复。
3. 工具结果写 `role="tool"`；真客户端改成 user，因为部分兼容接口不接受 tool 这个 role。

## 卡点
1. 不设步数上限 → 模型可以一直换参数。
2. 重复调用时继续执行 → 相同问题被计费、被重复写入。
3. 上限到达后，把某一次工具结果挑出来当最终答案 → 客人看不到「这是不完整的一轮」。
4. 解析失败让异常冒出请求 → 应消耗一步并写回「只输出 JSON」；步数仍然要算。
5. 以为换 hours=1/2/3 也算 `repeated_tool` → 签名含参数；换参靠 `max_steps`。
6. `max_steps=1` 时误以为正式回答仍是合计价 → 正式回答是上限句，价格只在 step 记录里。
