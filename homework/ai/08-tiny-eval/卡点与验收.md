## 复述
- 本课评的是**应用行为**（引用对不对、该不该拒绝、有没有走对工具），不是给模型打榜。Mock + 字面 TF-IDF 向量，测的是门槛、引用检查和工具循环。
- 9 条用例在 `eval_cases.json`：`kind` 分 `rag` / `agent`；`expect` 有 `cite`（不拒绝且引用含指定 `source_id`）、`refuse`（固定拒绝句、无引用）、`tool`（`final` 且步骤含指定工具）、`no_tool`（`final` 且零工具）。`forbid` / `require` 再扫回答片段。

- 期望不要写进系统提示；失败看 `reason`，不要放宽 `expect` 或删 `forbid` 迁就输出。
- 讲义建议把门槛抬到 0.99 看检索类变 `low_score`；本地用 `build_lab_rag(min_score=0.99)`，**不改**三仓 `DEFAULT_MIN_SCORE`。

## 原理（小白话）
- **评应用 vs 打榜**：通过率说明门槛/引用检查/工具循环有没有守住约定；Mock 剧本和字面向量不是模型能力分。
- **同句不同期望**：路径写进 `kind`，才知道是检索还是工具在干活；否则「答了」分不清功劳。
- **价格三件套**：规章路径禁单价、缺参反问、给了小时才工具出 `90`——证明数字来自允许列表里的纯函数。
- **失败不改期望**：放宽 expect / 删 forbid = 评测不再看守原来的坑；应看 `reason`（如 `low_score`）去修门槛或检索。
- **标准答案写进提示**：分数只说明模型会照抄，不能说明检索和引用检查在工作。

## 口头自查（自己答）
1. 评的是应用行为，不是排行榜；Mock 剧本 + 字面向量是假件，门槛/引用检查/工具循环是真代码。
2. 同句两路径：检索要引用规章且无单价；工具缺小时要反问不调用计价——合在一起才证明价格只来自工具。
3. 答案写进系统提示再打分，通过率只说明会照抄，测不出检索与引用检查。

## 卡点
1. 只放能答的题 → 拒绝和「不许猜价格」两种故障不会出现。
2. 用例不写路径（kind）→ 同句两条路径都「答了」，分不清是哪段代码。
3. 失败就放宽 expect / 删 forbid → 评测不再看守原坑。
4. 把 9/9 说成模型能力分 → 这里是 Mock + 字面向量，测的是你的门槛与循环。
5. 为演示高门槛去改三仓 `DEFAULT_MIN_SCORE` 却忘改回 → 本地用参数 `min_score=0.99`，源码不动。
6. 把期望写进系统提示 → 分数虚高，测不出检索/引用。
